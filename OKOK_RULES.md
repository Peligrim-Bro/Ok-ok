- Сборка: npm run build. Она проверяет итоговые файлы; ошибки останавливают также native Workers Builds.
- GitHub Actions проверяет мобильную верстку RU/EN/TH и offline PWA; Lighthouse запускается трижды, отчёты хранятся 14 дней.
- quality-budget.json ограничивает несжатый HTML, HTML gzip, весь JS и общий объём статических файлов. Это контроль роста сборки, а не измерение начальной загрузки.
- Lighthouse отдельно измеряет загрузку. Начальные пороги диагностические; повышение бюджетов допускается только после анализа причины.
- Независимая публикация Cloudflare не ждёт браузерного задания GitHub Actions. Не утверждать, что все Actions блокируют деплой.
- Сохранять текущий Service Worker с уникальным кешем, network-first навигацией и обходом /api/. Миграция на Workbox пока не требуется; делать её отдельным изменением с проверкой offline и обновления версий.
- После публикации проверить статус Cloudflare и commit в /build-info.json. Коммит сам по себе не подтверждает публикацию.

## Обязательный порядок перед публикацией изменений кода и вёрстки

1. Прочитать свежий main и сохранить уже внесённые исправления; не заменять файлы устаревшими копиями.
2. Собрать окончательную версию и выполнить проверки сборки, полный набор браузерных тестов и три запуска Lighthouse **до обновления main**: Cloudflare публикует автоматически.
3. Проверить RU/EN/TH, обе темы, телефон, планшет и горизонтальный режим. Просмотреть снимки; проверить пересечения, обрезание текста, навигацию, фильтры, закрытие прокрученных окон и восстановление позиции после чата. Регрессии закреплены в tests/layout.spec.cjs и tests/author-chat.spec.cjs; проверки шапки — также в verify-project.mjs.
4. При ошибке исправить и повторить затронутые проверки на окончательной сборке. Если обязательная проверка недоступна, не публиковать изменение; назвать конкретное ограничение. Не подменять проверку просьбой владельцу найти ошибки и не ослаблять тесты ради успешного результата.
5. После публикации подтвердить успешный Workers Builds: ok-ok, точный commit в /build-info.json и результат проверки живого сайта.

Проверки с имитацией виджета и эмуляцией размеров не выдавать за проверку настоящего tawk.to или физического iPhone. Изменения только документации требуют проверки текста и diff; повторять неизменённые тесты приложения не нужно.
